# G01 — Encrypted vault and recovery

**Status:** implementation in progress. No G01 deployment, acceptance, review or merge is claimed.

The current implementation verifies encrypted credential directories and the Calendar bind mount, pins directory handles across awaited operations, checks actual core-dump and cgroup swap controls, and provides the owner-only `vault-status` command. Calendar credential operations and backups now enforce process memory protection. Vault failure closes Google access while allowing the ordinary host store to open.

The kernel mount's device number must match exactly one encrypted block-device member with a valid filesystem UUID. Any UUID reported by `findmnt` must agree. Ambiguous devices and plaintext members remain denied. This works for a service user without granting raw-device access; older `findmnt` implementations probe devices directly. See [util-linux's cache implementation](https://github.com/util-linux/util-linux/blob/v2.41.2/libmount/src/cache.c) and [its lsblk property implementation](https://kernel.googlesource.com/pub/scm/utils/util-linux/util-linux/+/refs/tags/v2.41.1/misc-utils/lsblk-properties.c).

The development kernel fixture image is `sha256:12860b9566ab7fbd02d7182451825016dc84587ed5b4221447eb2d3487615e1c`. It uses `cryptsetup-bin` version `2:2.7.5-2` and `cifs-utils` version `2:7.4-1`. It runs offline with scoped loop/mapper access, zero core limits and zero permitted cgroup swap. Recovery material stays in a private pipe and memory; no recovery-key file is written. The root adapter tightens only its verified mapper inode to mode `0600`. Root administration verifies memory protection before handling keys; owner credential operations verify their own process controls. Docker's restricted kernel-keyring syscall requires the fixture's explicit direct dm-crypt key mode.

The fixture imports compiled development code through a read-only mount. It establishes development behavior only. It is not an immutable release test or a Pi acceptance receipt.
