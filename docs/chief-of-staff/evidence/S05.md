## Root usage, cancellation and local stop records

Commit `1391b38` adds host-owned mission inspection, atomic model/tool reservations, failure, bounded retry and cancellation transitions. Reservations count across the mission root and all attempts. Only the first successful caller receives `reserved: true`; an exact replay returns an accounting receipt with `reserved: false`, never permission for another invocation. Changed payloads or call kinds conflict. A lost commit acknowledgement consumes its reservation conservatively and cannot grant a duplicate call. Actual provider/tool integration must honor that distinction.

Retry requires the old attempt to be failed and independently confirmed stopped, unchanged current work-order authority, remaining root allowances and no other active or unconfirmed attempt. It allocates fresh group/session/attempt identities while preserving all prior usage and the original deadline. Retry replay returns the same identity. Cancellation increments the generation before native stop confirmation, closes pending approval work and prevents usage by stale identities. A mission remains `cancelling` until every exact child stop is confirmed; repeated cancellation does not advance the generation again. Owner inspection and stop remain available after source revocation or a paused scope. Foreign owner/session/group identities are refused.

Nine real-database scenarios pass for these transitions, including concurrent usage requests, retry/cancel races and lost usage-commit acknowledgement. The first six failed because the run store was absent. Their running-state fixture explicitly models completed native admission; it does not launch a worker. The shared attempt allocator now serves initial approval and retry, and all affected earlier approval/storage regressions pass: **49 external-database scenarios** in the combined suite.

Commit `7b31eb5` adds deny-only stop records to the host's native SQLite boundary. An attempt stop requires its exact permanent child marker; a family cancellation also fences identities allocated later. Stop records cannot grant permission or select ordinary groups. Five tests pass, including closing and reopening a real SQLite file, exact replay and independent later generations. The initial suite failed on the missing module. These are persistence and identity-boundary checks, not the full running-worker PostgreSQL-outage demonstration; dispatcher stop/reconciliation wiring is still pending.

All **1,806 host tests across 183 files** and host typecheck pass. Scoped lint has zero errors and nine existing-style explicit-any warnings in the new integration fixture; a `prefer-const` error was corrected. Formatting passes. No runner code changed in this increment; its most recent 176-test result remains the preceding approval-envelope regression. No new migration was needed: the separate test database remains at schema 7 and the accepted Pi release at schema 6.

## Native allocation and database dispatch leases

Commit `2aab112` adds a native allocator that persists intent before creating each attempt's permanent boundary, actual NanoClaw AgentGroup/session, private workspace, provider directory, host-control directory, exact context/template files and stable native input. It uses the existing native session schema and input writer. The child has no channel/thread binding, no destinations and no generic execution permission. Two real filesystem/SQLite fixtures have separate canaries and provider directories; no model response is used as isolation evidence.

Thirteen allocation scenarios pass. The initial suite failed on the missing allocator. The first implementation passed ten scenarios but the tamper fixture could not modify a deliberately read-only context file; the fixture now explicitly models trusted corruption before checking refusal. Each of seven interrupted allocation steps recovers the same group, session and input. Contradictory identities, changed payload/input, foreign pre-existing state, symlinks, altered context bytes, local cancellation and active-container rewrites are rejected. A later red test exposed silent replacement of lost provider state; completed steps now require their recorded state to remain present. Interrupted uncompleted steps can recover, while missing completed state requires recovery. Allocation paths are included in the stable payload digest.

Commit `fcfb122` makes the host mission store lease allocation under PostgreSQL row locks, with a 30-second owner lease and increasing dispatch fence. Another owner receives pending while the lease remains valid; after expiry, the old fence cannot authorize preparation or launch. Reclaiming preserves attempt identity, input ID, root usage and the original deadline. Source/context/template/private/provider authority is checked again before the exact source snapshot is returned. Marking a verified allocation ready still leaves the mission queued with no model/tool reservations. Only the restricted execution hook's separate guarded transition may mark it running. Revocation or cancellation overrides an earlier lease.

The two new lease scenarios first failed on missing methods, then passed. The combined affected external-database suite passed **51 scenarios**. All **1,819 host tests across 184 files** and host typecheck pass. Scoped lint has zero errors and 21 explicit-any warnings in the integration fixture; formatting passes. The previous 176 runner tests were not repeated because no runner code changed.

This is allocation and admission evidence, not a completed native worker run. The dispatch loop must still connect these operations to restricted launch and `wakeContainer`, preserve false wakes as pending, and reconcile exact native stops. Concrete mount/network tests, worker RPC/provider execution and the full Pi flow remain required.
